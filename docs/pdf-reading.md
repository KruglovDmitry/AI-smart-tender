# PDF в tools-server

Первый этап: организация существующего чтения PDF по формату. Модули создания и редактирования пока не добавлены.

## Структура

- `app/document_tool/pdf/read.py`: извлечение текста страниц, таблиц, PNG; простой текстовый fallback через pypdf.
- `app/document_tool/pdf/reader.py`: единый результат страницы (текст, источник, таблицы, структура, предупреждения); решения о необходимости OCR.
- `app/document_index/reading.py`: выбор полного чтения/индекса, выбранные страницы, бюджет ответа и продолжение.
- `app/document_tool/pdf/workflow.py`: совместимый импорт точки входа read_pdf без второй реализации.
- `app/document_tool/pdf/ocr.py`: локальное распознавание RapidOCR.
- `app/document_tool/pdf/vision.py`: вопрос к настроенной модели зрения по изображению страницы.
- `app/document_tool/pdf/SKILL.md`: инструкции модели по выбору инструментов и проверке источников.
- `app/document_tool/skills.py`: фиксированный реестр загрузки инструкций; пока только PDF.
- `app/document_index`: локальный постраничный индекс, поиск, кэш и навигация наших инструментов; это не векторная база RAG.
- `app/integrations/open_webui/loader.py`: адаптер /process, подготавливающий данные для RAG Open WebUI. Эмбеддинги, фрагменты и векторное хранилище обслуживает Open WebUI.

## Как модель получает skill

`GET /document_skill?file_type=pdf` включён в OpenAPI как обычный инструмент. Он возвращает текст инструкций и scope=tools-server, не читает пользовательские файлы и не вызывает LLM. `document_info` для PDF содержит подсказку загрузить skill. В `prompts/tender-agent-system.txt` есть соответствующее правило.

SKILL.md не исполняется автоматически из-за наличия на диске. Модель должна вызвать инструмент; существующий системный промпт в пользовательском интерфейсе надо обновить отдельно. Чтобы передать инструкции из собственного агентного цикла, можно вызвать `document_skill("pdf")` и включить возвращённые instructions в его контекст. Автоматическая загрузка навыков в фоновые табличные задания на этом этапе не добавлена.

Существующие read_document, document_info, search_document, read_pages и view_page сохраняют имена. Схемы вызовов совместимы с DeepSeek; поставщик основной модели не менялся. OCR локальный, модель зрения настраивается отдельно.

## Вложения чата

Вложения остаются на текущем пути Open WebUI. Подключение tools-server к чату не означает передачи ему вложений. Работа с ними не перехватывается автоматически, код и настройки Open WebUI этим изменением не меняются. Существующий внешний загрузчик /process сохранён; если он уже настроен в приложении, он продолжает работать через совместимые импорты.

## Проверка

Актуальный набор: 39 тестов документных/табличных инструментов, evidence и классификации, включая совместимость импортов, PNG, OCR-кэш, навигацию больших документов и отсутствие повторного извлечения структуры между адаптерами. Ответ OCR подменён; новые API моделей и скачивание OCR-моделей для этих проверок не требуются. Фактическое качество OCR на сканах и новая desktop-сборка этим прогоном не проверены. В desktop/build_tools_exe.ps1 добавлены новые модули и файл SKILL.md как ресурс.

## Материалы для сравнения

- [Anthropic: PDF support](https://platform.claude.com/docs/en/build-with-claude/pdf-support) — раздел How PDF support works: текст каждой страницы и её изображение для модели.
- [Anthropic: PDF skill](https://github.com/anthropics/skills/tree/main/skills/pdf) — инструкции и вспомогательные инструменты для программной обработки PDF. Документный навык source-available; его материалы не копировались в наш код.
- [OpenAI: File inputs](https://developers.openai.com/api/docs/guides/file-inputs) — прямой ввод PDF с текстом и изображениями страниц, требования к vision-модели и влияние на токены.
- [OpenAI: Code Interpreter](https://developers.openai.com/api/docs/guides/tools-code-interpreter) — другой слой: модель выполняет Python в изолированной среде для обработки файлов.

Наш текущий путь выбирает страницы локальными инструментами и возвращает текст/таблицы; изображения передаются отдельно при view_page. Это отличается от прямой передачи PDF мультимодальной модели. Полного совпадения с закрытыми реализациями ChatGPT или Claude не заявляем.


## Структура, большие PDF и QwenCloud

`read_pdf` — новая точка входа только для файлов tools-server. Auto читает до 8 страниц/40000 символов текстового слоя, иначе возвращает индекс до 40 страниц за вызов с next_outline_page. Это рабочие пороги, а не ограничения моделей. Для поиска факта используйте search_document и pages; для полного обхода mode=full и next_cursor. max_pages ограничен 10. text_offset продолжает содержимое страницы без пропуска текста или таблиц. Сохраняйте остальные параметры запроса и pages при продолжении. Покрытие между вызовами учитывает вызывающий агент; единого постоянного журнала полного обхода пока нет.

В layout указаны блоки текста, изображения и найденные таблицы с bbox в PDF points (верхний левый угол). Это геометрические эвристики: семантическая классификация заголовков, колонок и объектов не гарантируется. Найденные таблицы добавляются в содержание страницы в Markdown. Структура кэшируется; неудачное обнаружение таблиц повторяется. Текст ограничен max_chars, дополнительный layout — отдельным бюджетом 6000 символов; пропуски помечаются warnings. Ни один признак complete не доказывает смысловую правильность распознавания.

visual_mode=auto подключает vision для изображений, графики, пустого/повреждённого текстового слоя или OCR. Распознавание необходимости зрения эвристическое: для гарантированного визуального просмотра выбранных страниц используйте required. По умолчанию до двух попыток на запрос; оставшиеся страницы помечаются для view_page. При недоступности vision/OCR возвращаются предупреждения и страницы для проверки; отсутствие визуального результата не скрывается. Ошибочные страницы могут быть дочитаны отдельно.

view_page принимает bbox и detail=low|auto|high. Это локальный выбор DPI (100/настройка/250), не параметр детализации OpenAI. Число пикселей ограничено. Координаты объектов повернутых/нестандартных PDF могут потребовать отдельной проверки; простое геометрическое извлечение не заменяет визуальный анализ.

QwenCloud поддерживает используемый формат OpenAI-compatible image_url с base64: https://docs.qwencloud.com/developer-guides/multimodal/vision . Для ключа Сингапурского региона: TOOLS_VL_BASE_URL=https://ap-southeast-1.maas.qwencloudapi.com/compatible-mode/v1, TOOLS_VL_MODEL=qwen3-vl-plus. При пустом TOOLS_VL_API_KEY используется AV_PLANNER_API_KEY, затем QWEN_API_KEY. Фактический .env настроен на проверенный QwenCloud endpoint, ключ не копировался в исходники. Настройки основного DeepSeek не менялись.

Реальный тест на искусственной странице (TEST-001, 24 V DC, 10 A/250 V AC, схема A1–A2) прошёл: модель qwen3-vl-plus прочитала все четыре факта, около 8 секунд/2711 токенов. Это проверка интеграции, не оценка точности на реальных тендерах. Кэш vision учитывает вопрос, область, DPI, endpoint, модель и шаблон инструкции. Учёт usage возвращается при новом вызове. Полные PDF или Excel автоматически в vision не отправляются. Поддержка исходных офисных форматов остаётся отдельной; все файлы в PDF не конвертируются.

До объединения обработчиков: 36 локальных тестов, включая реальные геометрические таблицы, продолжение текста, автоматическое подключение vision с подменённым API и кэш структуры.

На искусственной таблице PyMuPDF 2.0 выделил штрих границы как пустую колонку шириной 2 points. Сырые данные не исправляются догадкой: добавлен table_grid_ambiguous, который помечает страницу неполной и рекомендует/в режиме auto подключает vision. Пустые колонки произвольно не удаляются.


## Общий обработчик без параллельных кэшей

DocIndex.read_page делегирует PDF-чтение PdfReader. Через него работают read_pages, read_pdf и внешний загрузчик /process. В document_tool/pdf/read.py осталась одна реализация обнаружения таблиц; page_tables — совместимая обёртка.

Структура и таблицы хранятся вместе в structure/<page>.json. Чтение только layout может создать неполную запись; первый запрос таблиц расширяет её, последующие используют готовую. Предупреждения о неоднозначной сетке сохраняются вместе с результатом; ошибки обнаружения не кэшируются как успех. Кэш атомарный, повреждённый JSON перестраивается. OCR использует тот же механизм хранения, но отдельную категорию. Версия индекса повышена до 5 (структурный DOCX); старые записи автоматически перестраиваются при обращении.

Загрузка через Open WebUI использует тот же обработчик с прежней политикой: без vision, таблицы только при <=40 страницах и текстовом источнике. Кэш OCR/структуры повторных загрузок идентифицируется SHA-256 содержимого, поэтому смена имени не вызывает повторного извлечения структуры. Первичное извлечение текста страниц загрузчик пока выполняет на каждом upload; между серверным файлом и загруженным в чат экземпляром общего кэша по содержимому нет. Их код обработки и формат результата общие. Политика Open WebUI и его векторная индексация не менялись.

Предупреждения передаются загрузчиком строкой в metadata, совместимой с обычными ограничениями векторных хранилищ. Параметры eval use_ocr/include_tables теперь явные, вместо подмены обходной функции. Проверки покрывают общий кэш между старым/новым инструментами, расширение layout таблицами, повторные uploads без vision, отключение таблиц и восстановление повреждённого кэша.


## Границы модулей

`document_tool/pdf` знает формат PDF и выполняет извлечение. `document_index` хранит локальный постраничный индекс, предоставляет поиск и управление чтением. `integrations/open_webui/loader.py` адаптирует результат для /process; своей реализации PDF-разбора и навигации не содержит. RAG-базу, эмбеддинги и поиск в знаниях обслуживает Open WebUI.

Устаревший пакет удалён вместе с его сборочными ссылками и тремя проверками совместимости. Все рабочие потребители (API, документы, табличные задания, eval, прогрев OCR в Docker/desktop) используют новые пути. Публичные HTTP-инструменты сохранили свои имена; внешний Python-код должен импортировать новые пакеты.
